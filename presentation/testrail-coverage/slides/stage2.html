СТАДИЯ 2 · РАЗРАБОТКА

Тест знает, какой кейс он закрывает

1. Найти существующие тесты

Старый кейс — метка на старый тест; новые тесты только на непокрытые шаги

2. Спроектировать тесты AT-xx

Архитектор в спеке или tester: уровень, AC, кейс и его шаги

3. Матрица по факту

tester фиксирует реальное покрытие; понижения — с причиной в changes.md

[Fact(DisplayName = "Пустой ИНН → 400")]
[Trait("TestRail", "C40214")]
public async Task Create_EmptyInn_Returns400()
{
  // Arrange · Act · Assert
}

Метка — разрешённое исключение из правила «без ссылок на тикеты в коде». Фильтр: dotnet test --filter-trait "TestRail=C40214"

Проверяют: spec-auditor — тесты обеспечивают обещанное покрытие; reviewer — ассерты соответствуют шагам кейса.

На стадии разработки три новых действия. Первое — если кейс уже существовал, сначала ищем старые тесты, которые его проверяют, и ставим метку на них, а не пишем дубль. Второе — тесты проектируются заранее списком: архитектор делает это в спецификации, а если архитектурного шага нет — tester. Третье — после написания тестов tester фиксирует в матрице, что реально покрыто. Если обещали «полностью», а вышло «частично», это видно, причина уходит в changes.md. Метка в коде — обычный атрибут Trait из xUnit. Мы явно разрешили его в стандартах, чтобы ревью не считало его трассировкой.
