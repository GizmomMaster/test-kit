# Proposal

## Why

QA-инженеры не знают, какие тест-кейсы TestRail уже закрыты unit- и интеграционными тестами разработчиков. Кейсы TestRail появляются только на стадии приёмки (`qa`), то есть после того, как автотесты написаны (`tester`, стадия 2). Поэтому тестам не на что сослаться, а приёмка повторяет вручную то, что уже проверено в CI. Источник требований (AC в BRD) общий у обеих сторон, но связи «требование → кейс TestRail → автотест» в конвейере AI SDLC нет.

## What Changes

- Проектирование тест-кейсов QA переносится на стадию 1: агент `qa` получает режим «дизайн» и пишет черновики кейсов (TC-xx) по AC эпика до работы `planner`.
- `analyst` вызывает `qa` между Гейтом 1 (одобрение BRD) и делегированием `planner`. Порядок стадии 1: analyst → qa → planner.
- `planner` раскладывает кейсы по срезам и в каждом `<slug>.plan.md` фиксирует **намерение покрытия**: уровень автотеста и ожидаемый статус (ПОЛНОСТЬЮ / ЧАСТИЧНО / НЕТ). От этого намерения считается оценка «автотесты Y ч».
- Намерение покрытия согласуется на Гейте 2 (разработчик + QA).
- Кейсы выгружаются в TestRail отдельным вызовом `qa` после того, как в Jira заведены подзадачи. Поле `refs` получает ключ среза, черновые TC-xx заменяются на C-id во всех артефактах.
- Вводится единая шкала покрытия по шагам кейса: «покрыт», «покрыт логически», «не покрыт». Из неё выводится статус кейса и правило о зависимости от стенда.
- На стадии 2 автотесты проектируются явно (AT-xx) с привязкой к AC и к шагам кейсов. Проектирует архитектор в плане верификации `spec.md`, а без архитектурного шага — `tester`.
- Автотест, закрывающий кейс, помечается `[Trait("TestRail", "C<id>")]`. Это явное исключение из запрета трассировочных ссылок в коде.
- `spec-auditor` проверяет, что AT-xx соответствуют намерению покрытия. `reviewer` проверяет честность трейтов и соответствие матрицы факту.
- Понижение покрытия на стадии 2 фиксируется в матрице и `changes.md` без отдельного гейта.
- Матрица покрытия ведётся машиночитаемым YAML-блоком в `test-cases.md`, набор файлов CI-контракта не меняется.
- Старые проекты переходят органически: когда задача переиспользует кейс, сначала ищутся существующие тесты на его шаги, и метка ставится на них, а новые тесты пишутся только на непокрытые шаги. Неоценённое покрытие («Не оценено») не приравнивается к «Нет». Массового сопоставления старых тестов и кейсов нет.
- Для QA формируется человекочитаемый отчёт покрытия: HTML-артефакт pipeline по кейсам задачи (покрытие, результат автотестов, что осталось проверить вручную), плюс JSON для агента `qa`. Джобу встраивают SRE по нашей спецификации, это внешняя зависимость. Без неё процесс работает по подтверждению пользователя.
- Фактическое покрытие после приёмки зеркалится в два новых пользовательских поля кейса TestRail (`Dev coverage`, `Dev autotests`). Поле State не трогаем: оно занято автоматизацией QA. Поля создаёт администратор TestRail, это внешняя зависимость. Без полей процесс работает по матрице.
- Приёмка учитывает покрытие. Кейс ПОЛНОСТЬЮ: один позитивный смоук-шаг на стенде, остальное из CI. ЧАСТИЧНО: вручную гоняются шаги без статуса «покрыт». НЕТ: полный ручной прогон.

## Capabilities

### New Capabilities

- `test-coverage-scale`: шкала покрытия кейса TestRail автотестами: статусы шагов, вывод статуса кейса, ограничения по уровню теста и зависимостям от стенда, формат матрицы покрытия.
- `coverage-planning`: стадия 1. Дизайн кейсов QA по AC, намерение покрытия в плане среза, согласование на Гейте 2, выгрузка в TestRail с заменой TC-xx на C-id.
- `autotest-traceability`: стадия 2. Проектирование AT-xx, пометка автотестов трейтом TestRail, аудит и ревью соответствия матрице, фиксация понижений покрытия.
- `qa-coverage-report`: отчёт покрытия для QA, который формируется в pipeline: содержимое по кейсам, пометки красных тестов и понижений, сверка матрицы с трейтами, привязка к сборке, JSON для агента.
- `coverage-aware-acceptance`: стадия 3. Объём ручной приёмки по статусу покрытия кейса, внесение результатов из CI в TestRail.

## Impact

- **agent-pack, canon:** `analyst.md` (субагент `qa`, новый шаг стадии 1), `qa.md` (режимы «дизайн», «выгрузка», «приёмка»), `planner.md` (раздел «Покрытие кейсов», оценка), `solution-architect.md` (AT-xx в плане верификации), `spec-auditor.md`, `tester.md`, `reviewer.md`, `coder.md` (исключение для трейта), `teamlead.md` (передача матрицы), `commands/task-start.md` (чек-лист стадий: коммит C-id после выгрузки).
- **agent-pack, refs:** `refs/qa/` (шкала покрытия, формат матрицы, режимы работы), `refs/qa/testrail-coverage.md` (search-before-design на стадии 1).
- **llm-wiki:** `topics/testing.md` (конвенция трейта TestRail, исключение из запрета трассировки), `topics/ai-sdlc.md` и `topics/ai-sdlc-contracts.md` (новый порядок стадии 1, артефакт `docs/tests/<EPIC>/test-cases.md`), `topics/testing-stack.md` (уточнение подписи BaseApiTest).
- **После правок canon:** регенерация `dist/` и `dist-manifest.sha256` (`scripts/generate.ps1`).
- **Внешние системы:** TestRail (`tr.dev.northwind-labs.test`), кейсы создаются раньше, чем сейчас. **Внешняя зависимость:** администратор TestRail создаёт поля `Dev coverage` (Dropdown) и `Dev autotests` (Text).
- **CI сервиса (внешняя зависимость, SRE):** Python-джоба отчёта покрытия после тестовых job'ов, артефакты `coverage-report.html` и `coverage-report.json`. Чтение TestRail из CI — сервисный доступ на чтение. CI-шаблон `cicd/components/unit-test` не меняется, но нужен спайк по выгрузке трейтов в JUnit-отчёт.
- **Вне скоупа:** автоматическая публикация результатов CI в TestRail, изменение CI-контракта артефактов задачи и общего шаблона `cicd/components/unit-test` (джоба отчёта добавляется в CI сервиса), Allure-отчёт, UI-автотесты.
