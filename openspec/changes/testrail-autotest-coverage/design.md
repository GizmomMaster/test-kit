# Design

## Context

Мотивация — см. `proposal.md`, раздел Why. Текущее состояние конвейера AI SDLC (agent-pack + llm-wiki), которое определяет подход:

- **Стадия 1:** `analyst` пишет BRD эпика (FR/BR/AC-xxx), проводит Гейт 1 и в той же сессии делегирует работу `planner`. `planner` нарезает эпик на срезы (`<slug>.plan.md`) и оценивает трудозатраты, включая «автотесты Y ч». Гейт 2 — согласование планов парой «разработчик + QA». Подзадачи и их Jira-ключи человек заводит **после** мастер-плана.
- **Стадия 2:** `teamlead` после `/task-start`. `solution-architect` работает только при архитектурном шаге в плане и пишет `spec.md` с планом верификации «AC → тест». Дальше `spec-auditor` → `coder` → `tester` → `reviewer`.
- **Стадия 3:** `qa` запускается человеком напрямую. Агент проектирует кейсы чёрным ящиком, выгружает их в TestRail (REUSE/UPDATE/CREATE), делает прогон через `curl` и пишет отчёт.
- **Ограничения:**
  - `analyst` не может вызвать `qa`: агента нет в списке субагентов.
  - План фиксирует состав работ, а не проектные решения.
  - Трассировочные ссылки в коде запрещены (`coder.md`, `solution-architect.md`, wiki `topics/testing.md`).
  - Агенты не придумывают ключи.
  - Имена артефактов задачи фиксированы CI-контрактом.
  - Стек тестов: xUnit v3, `Trait` поддерживается.
  - CI-шаблон запускает `dotnet test` в VSTest-режиме с `--logger junit`.
- **Устройство TestRail (по скриншотам проекта, 2026-11-26):**
  - Один suite на продукт: «Продукт А», 244 секции, 1495 кейсов.
  - Основная раскладка — по функциональной области: область → API/UI → версия API → секция на endpoint (например, `Документы / Сохранение документа и версии / API / API V4 / POST/api/v4.0/Document - Создать документ`).
  - Отдельная секция `Change Request` с подсекциями по Jira-ключам (`PRJ-4655`, …).
  - Поля кейса:
    - Type (например, `API`), Priority, Estimate;
    - References — может хранить несколько ключей (`PRJ-1307, PRJ-1342`);
    - State (например, `Automated`);
    - пользовательские поля `QA-Auto_Components` (сервис) и `QA-Auto_Tag` (наборы регрессии).
  - В предусловиях встречается блок «Для автотестов». State `Automated` означает, что кейс автоматизирован QA-инженерами по автоматизации (QA-Auto). Это отдельный слой автотестов, не unit- и интеграционные тесты разработчиков (подтверждено пользователем).
  - Новые кейсы задачи создаются в `Change Request/<KEY>`, а после релиза переносятся в функциональную секцию endpoint'а (подтверждено пользователем).
  - Шаги кейса — пары «действие → ожидание» (запрос → код ответа, проверка тела), что совпадает с единицей оценки шкалы покрытия.

## Goals / Non-Goals

**Goals:**
- Связь «AC → кейс TestRail (шаги) → автотест» видна QA уже на стадии 1 и подтверждается фактом на стадии 2.
- Изменения укладываются в текущие роли и гейты, без новых агентов и без правки CI-контракта.

**Non-Goals:**
- Автоматическая публикация результатов CI в TestRail: на первом этапе результаты вносит агент `qa` по отчёту CI.
- Покрытие UI и e2e-автотестами.
- Изменение CI-шаблона `cicd/components/unit-test`.
- Учёт автотестов QA-автоматизаторов (QA-Auto, State `Automated`) в матрице покрытия и при планировании.
- Запись результатов автотестов из CI в TestRail (результаты, прогоны). Pipeline только читает TestRail для отчёта.
- Allure-отчёт.
- Массовое сопоставление существующих тестов и кейсов старых проектов (D22). Пилот на приоритетной области — возможное отдельное изменение.
- Перенос кейсов из `Change Request/<KEY>` в функциональные секции после релиза: это остаётся работой QA.

## Целевой процесс

```
 СТАДИЯ 1
 analyst: BRD эпика (AC-xxx)
   [Гейт 1: одобрение BRD]
 qa (дизайн): docs/tests/<EPIC>/test-cases.md: TC-xx по AC, чёрный ящик
 planner: <slug>.plan.md + раздел "Покрытие кейсов" + оценка автотестов
   [Гейт 2: планы + покрытие: разработчик + QA]
 человек: подзадачи в Jira -> KEY срезов
 qa (выгрузка): search-before-design -> [HUMAN GATE] -> TestRail
                refs = KEY среза; TC-xx -> C-id в артефактах
 человек: коммит артефактов с C-id

 СТАДИЯ 2
 solution-architect (при арх. шаге): AT-xx в плане верификации spec.md
   или tester (без арх. шага): AT-xx до написания тестов
 spec-auditor: AT-xx соответствуют намерению покрытия
 coder -> tester: тесты, [Trait("TestRail","C<id>")], матрица в test-cases.md
 reviewer: трейты честные, матрица = факт
 tech-writer: понижения покрытия -> changes.md

 СТАДИЯ 3
 qa (приёмка): объём ручного прогона по статусу кейса; результаты в TestRail
```

## Decisions

**D1. Покрытие задаётся на двух уровнях: намерение на стадии 1, конкретные AT-xx на стадии 2.**
Архитектор работает на стадии 2, а у срезов без архитектурного шага `spec.md` нет вовсе. Намерение покрытия (уровень теста и ожидаемый статус кейса) — это объём работ, оно лежит внутри границы плана и обосновывает уже существующую оценку «автотесты Y ч». Отклонено:
- (а) перенос архитектора на стадию 1: ломает конвейер, `spec` строится по коду подмодулей;
- (б) матрица только на стадии 2: QA не получает картину заранее, а это и есть цель изменения.

**D2. Порядок стадии 1: analyst → qa → planner.**
Planner проходит один раз и получает все входы. Оценка автотестов опирается на кейсы, на Гейт 2 приходит полная картина. Отклонено:
- analyst → planner → qa → planner: второй проход planner'а;
- analyst → planner → qa, где намерение ставит qa: QA работает чёрным ящиком и не может выбрать уровень теста, оценка остаётся без опоры.

**D3. Черновые TC-xx хранятся на уровне эпика, выгрузка идёт после заведения подзадач.**
Ключей срезов на Гейте 2 ещё нет, а поле `refs` кейса = ключ задачи. Агентам запрещено придумывать ключи. Черновики лежат в `docs/tests/<EPIC>/test-cases.md`, выгрузку делает отдельный вызов `qa`, когда ключи появились. Так `refs` сразу правильный и второй проход по TestRail не нужен. Отклонено:
- выгрузка сразу после Гейта 2 с `refs` = ключ эпика и последующей дописью;
- черновики внутри `<slug>.plan.md`.

**D4. Кейс на стыке срезов относится к срезу, в котором закрывается последний из его AC.**
На приёмке этого среза функциональность кейса собрана целиком.

**D5. Шкала покрытия считается по шагам и имеет три статуса шага.** Подробно — в спецификации `test-coverage-scale`. Промежуточный статус «покрыт логически» нужен, чтобы QA видел, что правило уже проверено unit-тестом. При этом шаг остаётся в ручном прогоне: unit-тест не доказывает, что endpoint применяет правило. Отклонено: два статуса без учёта unit-тестов, при них теряется видимость проверенных граничных значений.

**D6. Метка автотеста — штатный `[Trait("TestRail", "C<id>")]`.**
Не нужен новый пакет, работает фильтрация `--filter-trait`, есть прецедент `[Trait("Performance")]`. На тесте можно поставить несколько трейтов, у кейса может быть несколько тестов. Номера шагов в трейт не пишутся, они живут только в матрице. ID AT-xx и AC в код не попадают. Отклонено: свой атрибут (нужен общий пакет), соглашение об именовании тестов (хрупко, противоречит конвенциям имён Регламента).

**D7. Явное исключение из запрета трассировки.**
Трейт TestRail — разрешённая метка, а не трассировочный комментарий. Исключение записывается в wiki `topics/testing.md` и в каноны `coder`, `tester`, `solution-architect`, `reviewer`, иначе ревью будет его отклонять.

**D8. Матрица стадии 2 ведётся разделом в `test-cases.md` среза.**
Набор файлов CI-контракта не меняется. На стадии 1 намерение лежит в `<slug>.plan.md` (раздел «Покрытие кейсов»).

**D9. Три точки подтверждения.**
- Гейт 2 (QA-человек и аналитик): намерение покрытия.
- `spec-auditor`: AT-xx соответствуют намерению. Расширяет существующую проверку «каждый AC покрыт».
- `reviewer`: ассерты теста соответствуют шагам кейса, указанного в трейте.

Понижение покрытия на стадии 2 отдельным гейтом не делается: оно записывается в матрицу с причиной и выносится в `changes.md`, QA видит его на приёмке.

**D10. Приёмка кейса со статусом ПОЛНОСТЬЮ — один позитивный смоук-шаг на стенде, остальное из CI.**
Интеграционные тесты на WAF и Testcontainers не проверяют стенд, конфиг и авторизацию, смоук закрывает этот риск дёшево.

**D11. Выгрузку в TestRail запускает отдельный вызов `qa`.** Это ответ на D3. Решение R8 (выгрузку запускает analyst в той же сессии) заменено, потому что ключей к тому моменту ещё нет.

**D12. Поиск существующего покрытия — в функциональной секции endpoint'а, REUSE — основной случай.**
Кейсы лежат по функциональным областям и endpoint'ам, а база большая (~1500 кейсов). Поэтому новая задача почти всегда затрагивает уже покрытый endpoint. Search-before-design на стадии 1 (режим «дизайн») ищет кейсы в секции каждого затрагиваемого endpoint'а (и в секции области для UI). Также он ищет в подсекциях `Change Request/*`: там лежат ещё не перенесённые кейсы других задач, которые трогают тот же endpoint. Найденный кейс, покрывающий требование, попадает в черновики не как новый TC-xx, а сразу с C-id и решением REUSE или UPDATE. Тогда planner видит его в намерении покрытия наравне с новыми. Отклонено: поиск только в целевой секции выгрузки (`Change Request/<KEY>`), он пропустит почти всё существующее покрытие.

**D13. При REUSE/UPDATE ключ среза дописывается в References, а не заменяет его.**
References у кейса может хранить несколько ключей. Перезапись потеряла бы трассировку к прежним задачам.

**D14. Поле State кейса для покрытия автотестами разработчиков не используется.**
State `Automated` означает автоматизацию силами QA-автоматизаторов (QA-Auto). Это подтвердил пользователь. Запись туда покрытия unit- и интеграционными тестами смешала бы два смысла и сбила бы планирование QA-автоматизации. Новые значения внутри State тоже отклонены: поле одно значное, а кейс может одновременно быть автоматизирован QA и покрыт тестами разработчиков.

**D17. Покрытие зеркалится в два новых пользовательских поля кейса TestRail; источник правды — матрица.**
Рабочие названия полей (окончательные выбирает администратор TestRail):

| Поле | Тип | Содержимое |
|------|-----|-----------|
| `Dev coverage` | Dropdown | `Не оценено` (по умолчанию) / `Нет` / `Частично` / `Полностью`: статус кейса по шкале покрытия. `Не оценено` ≠ `Нет`, см. D22 |
| `Dev autotests` | Text | номера шагов по статусам («покрыт», «покрыт логически»), автотесты, строка «сверено: <KEY>, <дата>» |

- **Кто и когда пишет:** агент `qa` на стадии 3 после приёмки, по фактической матрице. Факт к этому моменту подтверждён ревью и зелёным CI. Намерение со стадии 1 в поля не пишется, оно ещё может измениться. Запись идёт под HUMAN GATE вместе с внесением результатов.
- **Кто и когда читает:** агент `qa` на стадии 1 при поиске существующего покрытия (D12) читает поля как подсказку. Решение о покрытии принимается по фактическим тестам в репозитории (поиск трейта `C<id>`), потому что поле могло устареть.
- **Защита от устаревания:** строка «сверено: <KEY>, <дата>» показывает, когда покрытие сверялось последний раз.
- **Почему:** QA работает в TestRail, а не в репозитории. Поле видно в кейсе, фильтрах и отчётах и переезжает вместе с кейсом при переносе из `Change Request` в функциональную секцию. При REUSE оно сразу показывает прежнее покрытие.
- **Отклонено:**
  - только матрица: QA не видит покрытие в TestRail, при REUSE прежнее покрытие теряется;
  - одно поле `Dev coverage`: нет защиты от устаревания и нет ссылок на тесты.

**Внешняя зависимость:** поля создаёт администратор TestRail (Administration → Customizations → Case Fields). Агенты поля не создают. Механизм на инстансе уже используется (поля `QA-Auto_*`), но права и согласование — за администратором. **Пока полей нет, процесс не блокируется:** покрытие ведётся только в матрице, агент `qa` пропускает запись полей и отмечает в отчёте «поля покрытия в TestRail отсутствуют».

**D16. Новые кейсы выгружаются в `Change Request/<KEY>` среза.**
Так принято на проекте. Перенос в функциональную секцию после релиза делает QA, агенты в нём не участвуют. Если подсекции `<KEY>` нет, агент `qa` создаёт её под HUMAN GATE выгрузки. Сейчас в скилле `testrail-api` есть только `get_sections.sh`, скрипт создания секции (`add_section`) нужно добавить (bash и PowerShell). Отклонено: выгрузка сразу в секцию endpoint'а, она расходится с текущей практикой QA.

**D18. Без архитектурного шага `tester` записывает AT-xx прямо в матрицу `test-cases.md` среза.**
Запись делается до написания тестов, с пометкой «спроектировано tester'ом». Тогда у всех срезов одно место, reviewer сверяет один файл, а `plan.status.md` остаётся только для статусов. Отклонено: `plan.status.md` (смешивает статусы и проектирование).

**D19. Отчёт покрытия для QA — HTML-артефакт pipeline, который строит Python-джоба в CI сервиса.**
Отчёт построен по кейсам, а не по тестам. Он соединяет три источника: матрицу (кейсы, шаги, статусы, тесты, понижения), результаты unit- и интеграционных job'ов и названия кейсов из TestRail (только чтение). Ссылку на артефакт QA открывает из MR. Требования к содержимому — спецификация `qa-coverage-report`.
- **Почему CI:** данные о прогоне есть только у pipeline, и только он гарантирует соответствие отчёта коду и SHA.
- **Отклонено:**
  - Allure как отчёт для QA: он построен вокруг тестов и не знает шагов, статусов покрытия и ручного остатка. Его можно подключить позже отдельно, как отчёт по тестам;
  - Markdown, который формирует агент в конце стадии 2: результаты локальные и устаревают после правок ревью;
  - отчёт, который собирает агент qa на стадии 3: нужен доступ агента к GitLab;
  - комментарий в MR: ограничен по объёму.

**Внешняя зависимость:** джобу встраивают SRE по нашей задаче. Наша часть — договор: схема матрицы (D20) и спецификация `qa-coverage-report`. Пока джобы нет, QA-человек смотрит pipeline сам, а агент `qa` получает подтверждение статуса тестов от пользователя с пометкой в отчёте.

**D20. Матрица — YAML-блок в `test-cases.md` среза.**
Python-джоба должна надёжно разбирать матрицу, свободная Markdown-таблица для этого хрупка. Агенты пишут YAML так же легко. Набросок схемы (окончательная — в `refs/qa/`):

```yaml
coverage:
  key: PRJ-4812
  cases:
    - case: C40214          # до выгрузки: TC-02
      ac: [AC-002]
      planned: full            # намерение со стадии 1: full | partial | none
      actual: partial          # факт после стадии 2
      steps:
        covered: [1]
        logical: [2, 3]
      tests:
        - name: Documents.Api.Tests.CreateDocumentApiTests.Create_EmptyInn_Returns400
          steps: [1]
        - name: Documents.Unit.Tests.InnValidatorTests.Validate_WrongLength_Fails
          steps: [2, 3]
      downgrade: "лимит длины ИНН задаётся конфигом стенда"   # если actual < planned
      reason: null             # для none: причина (C4)
      origin: architect        # architect | tester | stage2-added | existing (старый тест, трейт поставлен в этой задаче)
```

Тесты указываются полными именами, как в результатах прогона: джоба сопоставляет по ним, поэтому спайк E1 (трейты в JUnit) для отчёта не обязателен. Трейты в коде сверяются с матрицей как дополнительная проверка. Отклонено: Markdown-таблица со строгими колонками (хрупкий разбор, многострочные значения).

**D21. Агент `qa` получает результаты CI из `coverage-report.json`, который ему передаёт пользователь.**
Доступа к GitLab у агента нет (скилл `corp-gitlab` умеет только искать и клонировать репозитории), и мы его не добавляем. QA-человек скачивает JSON-артефакт рядом с HTML и передаёт агенту. Отклонено: чтение pipeline агентом через GitLab API (новый скрипт и доступ ради того, что уже делает джоба).

**D22. Старые проекты: покрытие связывается органически, только для кейсов, которые затрагивает задача.**
На старом проекте есть тысячи кейсов и сотни тестов без трейтов. Массового сопоставления не делаем. Связь появляется, когда задача берёт кейс через REUSE/UPDATE:
- **Стадия 1 (`qa`):** кейс без трейтов в коде помечается «покрытие не оценено». Это не то же самое, что «не покрыт».
- **Стадия 1 (`planner`):** для такого кейса в намерение покрытия и оценку входит поиск существующих тестов.
- **Стадия 2 (архитектор или `tester`):** до проектирования новых AT-xx ищутся существующие тесты на шаги кейса. Найденный тест получает трейт и попадает в матрицу с `origin: existing`. Новые тесты пишутся только на непокрытые шаги, дублирующие тесты не пишутся.
- **Стадия 2 (`reviewer`):** трейт на старом тесте проверяется по тем же правилам, что и на новом.
- **Без оценки не равно «Нет»:** пустое или `Не оценено` в `Dev coverage` и отсутствие трейтов означают «не оценивали». Агенты и отчёт не трактуют это как НЕТ.

Отклонено:
- массовое сопоставление всех тестов со всеми кейсами сервиса: дорого, а точность сопоставления «по коду» плохо проверяется;
- «ничего не делать»: дубли тестов и ложные «не покрыт» на каждом REUSE.

Пилот на приоритетной области (сопоставить один раздел целиком) возможен позже отдельным изменением.

**D23. Метка в проектах не на xUnit.**
В xUnit v2 и v3 используется `Trait`. Для NUnit (`[Property]`) и MSTest (`[TestProperty]`) эквивалент с тем же ключом `TestRail` и значением `C<id>` фиксируется в `refs/` и wiki при первом применении в таком проекте. Джоба отчёта опирается на имена тестов из матрицы (D20), поэтому от фреймворка она не зависит.

**D15. Type кейса для API-проверок — `API`.**
На проекте API-кейсы имеют Type `API`, а не `Functional`, как по умолчанию в формате кейса `qa`. Значение по умолчанию в `refs/qa/testrail-format.md` берётся из существующих кейсов секции, а не из таблицы.

## Risks / Trade-offs

- [Расхождение намерения и факта: обещали ПОЛНОСТЬЮ, получилось ЧАСТИЧНО] → понижение видно в матрице и `changes.md`. Приёмка опирается на фактическую матрицу, а не на намерение.
- [Ложное «ПОЛНОСТЬЮ»: трейт стоит, а ассерты не покрывают шаги] → проверка `reviewer` по шагам кейса (D9). Смоук на приёмке (D10) остаётся страховкой.
- [Кейсы создаются в TestRail до разработки, требования могут измениться] → выгрузка после согласования планов. При изменениях действует таксономия REUSE/UPDATE из `refs/qa/testrail-coverage.md`.
- [Стадия 1 удлиняется на шаг qa] → дизайн кейсов не требует стенда и прогона. Он и так выполнялся позже, теперь он просто перенесён.
- [Правка согласованного плана (замена TC-xx на C-id) после Гейта 2] → правка механическая, повторного согласования не требует. В чек-лист `task-start.md` добавляется коммит этих правок.
- [Поля `Dev coverage` / `Dev autotests` устаревают: тесты удалили или переписали после закрытия задачи] → поле служит только подсказкой, решение принимается по трейтам в репозитории. Строка «сверено: <KEY>, <дата>» показывает давность. Каждая новая задача, затронувшая кейс, перезаписывает поля на стадии 3.
- [На старом проекте tester не найдёт существующий тест и напишет дубль] → поиск существующих тестов обязателен до проектирования AT-xx, reviewer видит в diff новые тесты рядом со старыми на тот же endpoint.
- [Картина покрытия старых областей долго остаётся «Не оценено»] → принятая цена органического подхода. При необходимости — пилот отдельным изменением.
- [SRE не успеют встроить джобу отчёта] → процесс работает без неё: QA смотрит pipeline сам, агент qa получает подтверждение от пользователя (D19, D21).
- [Агент пишет невалидный YAML матрицы] → отчёт сообщает об ошибке разбора, а не строится по частичным данным. Reviewer проверяет матрицу на стадии 2.
- [Тест переименован после записи в матрицу] → отчёт помечает «тест не найден», и кейс уходит в полный ручной прогон. Расхождение матрицы и трейтов отчёт выводит предупреждением.
- [На стенде развёрнута не та сборка, по которой построен отчёт] → в отчёте указан SHA. Сверка SHA со стендом остаётся за QA.
- [Администратор не создаст поля или затянет с этим] → процесс работает по матрице, поля — улучшение, а не условие (D17).
- [Без JUnit-трейтов сопоставление «C-id → результат CI» ручное] → резерв: статическое сопоставление трейтов по коду, результат по имени теста (см. Open Questions).

## Migration Plan

0. **Внешняя зависимость, параллельно с остальным:** запрос администратору TestRail на создание полей `Dev coverage` (Dropdown) и `Dev autotests` (Text) для проекта. После создания нужно получить системные имена полей (`custom_*`) и значения Dropdown через `get_case` любого кейса и записать их в `refs/qa/testrail-format.md`. До этого шаги ниже работают без полей.
0а. **Внешняя зависимость, параллельно с остальным:** задача SRE на Python-джобу отчёта покрытия. Входы задачи — спецификация `qa-coverage-report` и схема матрицы из `refs/qa/` (D20). Ставить задачу можно, когда схема матрицы зафиксирована.
1. Правки llm-wiki (`topics/testing.md`, `topics/ai-sdlc*.md`): конвенция и процесс.
2. Правки canon и refs agent-pack, затем регенерация `dist/` и манифеста (`scripts/generate.ps1`, `scripts/validate.sh`).
3. Пилот на одном эпике. Задачи, уже прошедшие стадию 1, продолжают работать по старому процессу: `qa` на стадии 3 при отсутствии матрицы ведёт себя как сейчас.
4. Откат — revert правок canon/refs/wiki. В TestRail остаются только обычные кейсы, трейты в тестах ничего не ломают.

## Open Questions

- **Окончательные названия и системные имена полей покрытия:** задаёт администратор TestRail (D17). Рабочие названия — `Dev coverage`, `Dev autotests`.

- **Где живёт скрипт джобы отчёта:** в репозитории сервиса, в общем CI-репозитории (рядом с `cicd/components/unit-test`) или в agent-pack. Решают SRE при постановке задачи, на спецификацию отчёта это не влияет.
- **Формат результатов тестов для джобы:** JUnit (уже выгружается шаблоном) или TRX. Решают SRE. Отчёту нужны только полные имена тестов и их статусы.
- **Трейты в JUnit-отчёте CI (E1):** теперь некритично (D20). Если трейты выгружаются, джоба может сверять их без сканирования кода. Если нет — статическое сопоставление «трейт → тест» по коду.
- **Кейсы не про API:** что считать «тем же интерфейсом» для фоновых обработчиков. Пока такие кейсы получают максимум ЧАСТИЧНО.
